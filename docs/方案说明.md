# 方案说明 · 设计取舍与踩坑记录

## 一、为什么是这个架构

### 需求约束

| 约束 | 说明 |
|---|---|
| 服务器位于内网 | 无公网 IP，外部无法主动连接 |
| 内网可出网 | 服务器能主动向外发起请求 |
| 已有 frp 通道 | 已具备内网穿透能力，可复用 |
| 不引入登录类凭据 | 方案不应依赖 SSH 私钥直连，降低凭据外流风险 |

### 方案选型对比

| 方案 | 可行性 | 说明 |
|---|---|---|
| **A. 定时任务 SSH 直连内网** | ❌ 不可行 | 内网无公网 IP 外部进不来；且需搬运私钥，安全风险高 |
| **B. 主动推送 + 对象存储中转** | ✅ 可行 | 内网能出网即可，零运维，历史可留痕 |
| **C. 主动推送 + 自建公网服务** | ✅ 可行 | 需自备公网服务与存储 |
| **D. frp 透传 + 公网侧拉取** | ✅ **采用** | 复用已有 frp，改造成本最低 |

### 为什么选 D

1. **已有 frp 基础设施**，改造成本最低
2. 打通后公网侧就是一个**普通 HTTP 端点**，消费方（定时任务/脚本/浏览器）都能读
3. **全程不需要 SSH、不需要私钥、不需要公网 IP**
4. 相比 B，**不需要额外的对象存储账号和上传凭证**

> 若 frp 不可用或不愿暴露服务，可退回方案 B（对象存储中转）。

## 二、关键设计点

### 1. 时间戳是失联检测的唯一依据 ⭐

**这是整套方案最容易漏掉的一点。**

链路断开以后，`status.json` 的内容**不会变** —— 公网侧读到的还是最后一份旧数据，看起来一切正常。

所以消费侧**必须**校验时间戳的新鲜度（用 `checked_at_epoch`，免去解析时区）：

```
请求失败                         → 链路断了
now - checked_at_epoch > 900 秒  → 数据失联（服务或 frpc 掉线）
```

**光看 `healthy == true` 是不够的。**

### 2. 实时性边界

数据新鲜度上限 = 内网 crontab 周期（默认 5 分钟）。
公网侧拉取频率可以更低（比如 15 分钟），因为内网侧才是真正决定实时性的地方。

### 3. 只暴露单个路径

```
location = /status.json { ... }
location / { return 404; }     # 其余一律拒绝，避免目录被枚举
```

**不要整目录对外。**

### 4. 只映射回环地址

```
localIP = "127.0.0.1"    # ⚠️ 关键
```

**不要把内网服务器整机端口映射出去。**

### 5. 静默设计

一切正常时**零输出、零打扰**。
只有「真动手修了东西」或「需要人拍板」才吭声。

这靠 cron 的看门狗模式实现：`stdout 为空 → 不发送任何消息`。

## 三、判定口径的取舍

### 为什么用「周期 × 2.5」而不是严格按周期？

任务偶尔晚几分钟是正常的。严格按周期判会导致**大量假警报**，而假警报比漏报更烦人 —— 一旦人开始忽略通知，监控就失效了。

2.5 倍是个经验值：既能容忍抖动，又不会漏太久。

### 为什么备份失败不自动重跑？

备份失败的原因可能是：
- 磁盘满了（重跑还是失败）
- 权限变了（重跑还是失败）
- 上游服务挂了（重跑可能更糟）

**自动重跑可能越修越坏**，而且会覆盖掉失败现场。所以只报告，让人判断。

### 为什么自愈只做「重启」？

重启是**可逆**操作，最坏情况就是没修好。而改配置、改凭据是不可逆的，一旦自动执行错了，代价远大于收益。

**红线**：改配置 / 改凭据 / 改密码 / 重启整机 —— **绝不自动**。

## 四、踩坑记录

### 1. 免费 frp 站只放行特定端口段

加了 proxy 后 frpc 报：

```
[watcher-http] start error: port not allowed
```

**原因**：免费 frp 服务商通常只放行**特定端口段**（比如 4315x），不是任意端口都能用。

**解决**：批量试几个候选端口，看哪个能起来，再收敛到确定的那个。

### 2. 巡检脚本不能只看进程存活

最初的版本是 `pgrep -x nginx` —— 这只能回答「nginx 还在吗」。

但真正的问题是「**昨晚的备份跑完了吗**」。所以后来改成：

- 读每个任务的 cron 表达式 → 算出它**本该多久跑一次**
- 对比 `last_run` → **超过 2.5 倍就判逾期**
- 加上关键链路的深度检查（备份日志新鲜度、抓包文件是否还在增长）

**进程活着 ≠ 在干活。**

### 3. 日志文件时间是判定的基础，也是软肋

crontab 类的任务没有 `last_run` 字段可读，只能靠**日志文件的修改时间**推断。

**软肋**：如果某个任务根本不写日志，就会被误判。所以：
- 每个被监控的 crontab 任务**都应该有对应日志**
- 没有日志的，先补日志，再纳入监控

### 4. `pgrep -x` 是精确匹配

`pgrep -x java` 匹配不上以完整路径启动的 `/usr/bin/java`。
这种情况要改用 `pgrep -f` 或调整匹配串。

### 5. 服务快照可能过期

自愈脚本读到的是几分钟前的 JSON 快照。**动手前必须重新确认**目标是不是真的还死着：

```python
if is_active(name, scope):   # 先确认
    continue                 # 已经活了，别动
```

否则会出现「重复重启」「把已经好的服务又重启一遍」。

### 6. 「服务挂了」有一半是探针写错了

巡检报某服务 401 → 判定挂了。手动一测：`GET /` 返回 `200 {"status":"ok",...}`。

**真相**：探针用了 `POST` 且没带 key，服务回 401 是**正确行为**，不是故障。

**教训**：报「服务挂了」之前，先用**最朴素的方式**手工复现一次。
探针方法错、探针路径错、探针缺参数 —— 都会伪装成服务故障，而且**每次巡检都稳定复现**，
看起来特别可信。

### 7. 被主动停用的服务 ≠ 故障

某个常驻服务一直报 `inactive`，查了半天以为该活却死了。

最后翻 systemd 单元文件的 drop-in 配置，里面白纸黑字写着：

```
# 2026-10-12 用户要求「永远关闭」，恢复 Restart=no
```

**是用户主动关的，不是故障。**

**教训**：常驻服务报 inactive 时，**先去读单元文件和 drop-in 里的注释**，
再判断是不是故障。监控项「该活」这个前提，本身也需要证据。

### 8. 幽灵服务会天天误报

清单里有一批服务，`systemctl status` 返回 `Unit xxx.service not found` ——
**本机根本不存在这些单元**，但巡检天天把它们列为异常。

**原因**：清单是从历史配置里抄来的，服务早就被删了，清单没跟着删。

**解决**：巡检前先做一次 `svc_exists()` 检查 —— 单元不存在就跳过并标记，
而不是当成「服务死了」。自愈脚本同样要跳过，否则会不断尝试重启不存在的东西。

### 9. 监控清单必须让用户拍板

一开始自己列了一堆「重要服务」纳入监控，结果用户看了说：
**「这些要，没有的不要」「先不管，临时项目」**。

**教训**：监控范围是**用户的决定**，不是技术判断。
列清单 → 交给用户勾选 → 按回传定稿。
用户说「不要」的标**已取消**（不删除，留痕）；说「先不管」的**既不监控也不停**。

### 10. 台账数字是动态的，别硬编码

文档里写了「共 43 项」，过几小时变 45 项 —— 因为期间新增了 2 个定时任务。

**教训**：消费侧**只判断语义字段**（`healthy` / `problems` / `checked_at`），
**不要**把 `total_checked`、任务数这类计数写进判断逻辑或断言。
它们会变，变了不是异常。

## 六、不要做的三件事

1. ❌ **不要把内网服务器整机端口映射出去**（只映射回环上的单个 HTTP 端口）
2. ❌ **不要用 SSH 私钥去做这件事**（本方案全程不需要 SSH）
3. ❌ **不要把 token / 密码写死在脚本里或提交到代码仓库**
